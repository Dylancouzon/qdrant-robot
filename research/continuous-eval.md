# Continuous evaluation design (F0d)

D91 freezes the data. This task builds measurement, without changing product answers, retrieval, models, or old fixtures. F0 found an evidence bottleneck (D87). A fixed continuous baseline must establish the next comparison before builders improve evidence. J means measured on Jetson; E means measured elsewhere; U means proposed or unverified.

## Alternatives and choice

Option A extends `eval/replay.run` with timed sessions, incremental logging, and optional reset behavior. Measure schedule lateness, failure propagation, code size, and old replay regression checks. It reuses scoring but adds branches around relative audio pacing, reset, inline rubrics, and unbounded joins.

Option B adds a small `eval/continuous.py` evaluator for absolute schedules. Keep one Robot and one FileCamera, reuse audio loading and existing row scoring where useful, and log every event incrementally. Measure the same timing and failure checks, then run a short Jetson development smoke. Prefer B because continuous data has separate rubrics and no reset semantics. Keep legacy replay unchanged. Do not build another runtime, generic orchestration framework, camera thread, or persistence layer.

## Scope and builder interface

Allowed implementation: `eval/continuous.py`, `eval/test_continuous.py`, and a minimal `eval/make_wavs.py` output-directory argument. The lead owns integration, bookkeeping, generated challenge audio, scoring, and remote jobs. No robot module changes, dependencies, model settings, prompt changes, or frozen-data edits. The builder receives schema examples with invented test text and must not read challenge sources, wording, expected answers, or baseline failures. The builder can read `eval/challenge-20261009/training-exclusions.json` only.

Input is JSONL visits containing `id`, `start_at_s`, `duration_s`, `continuous_process: true`, `restart: false`, and ordered `steps`. Every step has unique `id`, absolute `at_s`, exactly one of relative `show` or `say`, and `scored`. Show events also have `source_id` and `hold_final_frame_until_s`. Questions may have `category`. Audio is a separate directory of 16 kHz mono signed-16 WAVs named by step ID. The evaluator never reads rubrics or expected facts. Reject duplicate IDs, invalid paths, overlapping visits, missing audio, incompatible WAVs, or speech extending into the next event before loading Robot.

Use synthetic WAVs for this baseline so VAD, ASR, retrieval, generation, TTS, and detection remain active. Set wake_word=False, as ordinary scripted replay does. File input and queued synthesis do not establish physical audible latency. Oracle input would diagnose language alone and cannot replace this continuous baseline.

## Scheduling and completion

Construct the Robot once with a fresh run-owned memory directory. Record startup separately. Start the single monotonic schedule after successful Robot initialization, and use a matching wall anchor for source evidence. Never reset or restart between visits. Submit all show and say events at their absolute times. Feed audio in 80 ms chunks and silence between utterances, with one scheduler owning `hear`. Chunk deadlines mark sample ends: the first full chunk arrives at utterance at_s + 0.08 s, and the final partial chunk arrives at its actual sample end. This matches Ears.wall(), which anchors the end sample to arrival wall time. Show and say event starts stay at their specified at_s. Keep continuous silence at the same sample-end cadence, and preserve at least 1.5 s endpoint silence after each WAV. Audio preflight rejects a WAV plus endpoint silence that overlaps the next utterance. Keep the clock fixed. Record due time, actual time, lateness, source changes, speech end, and returned turns. U: a step or chunk more than 0.5 s late fails timing. Record the failure instead of shifting later events.

Collect turns without blocking the scheduler. Associate them by Turn.speech_start and speech_end against actual input WAV intervals, with a fixed 0.25 s buffering tolerance. Never use queue order or turn return time for association. Both timestamps must match exactly one interval; ambiguous or unmatched turns fail operations. Delayed ASR retains its original interval. A split remains a failed step, and an empty transcript produces an explicit failed row for its original interval. Complete queued processing for each utterance before the next say event. If a previous answer or pending turn work prevents association, fail rather than reuse another question's turn. Output includes all 63 spoken events, their scored flag, category, heard text, answer, saved WAV path, stage timestamps, retrieved evidence IDs, source mapping, and input-file hashes. Keep auxiliary statements unscored but logged. A dropped transcript, split, empty answer, or question miss is a failed step, recorded without changing the schedule. Missing scheduled inputs, stalled pending work, or misassociated turns are operational failures.

Write metadata before startup, flush event/turn rows immediately, and emit progress every second. A separate supervisor process publishes the final completion footer only after the evaluator worker exits zero, including native interpreter teardown. The worker must first record the full visit duration, all expected event/utterance IDs, required component liveness, final turn drain, and successful bounded cleanup. Record expected/actual scored, auxiliary, show, and visit counts plus elapsed time. Failure writes an error row and exits non-zero without a completion footer. A completed baseline can have poor answer scores, which later independent judging reports. The supervisor returns non-zero for failed steps after publishing a completed run footer when the worker completed cleanly. It omits the footer for operational failures or any non-zero worker exit. Correctness is judged separately against frozen rubrics.

## Progress, resource measurements, and recovery

Required Robot threads `_watch`, `_detect`, `_transcribe`, and `_work` must stay alive. Check `detect_failed`, llama-server child liveness, detector count progress, and scheduler/audio progress at least once per second. This catches FileCamera exceptions that kill a thread before `detect_failed` is set (D90 carried risk). U: while frames are available, no detection increment for 10 s fails the run. Native source/Robot initialization or shutdown can block Python. A separate supervisor process reads incremental phase/progress rows and polls worker status. It must survive a blocked or stopped worker interpreter. On a frozen phase timeout or non-zero worker exit, write an error row, kill the worker process group including llama-server, reap the worker, and omit completion. Launch the worker in a new process group. A completion-ready row cannot authorize a footer before zero process exit. Startup has 180 s, source switching 10 s, final cleanup 60 s; ordinary schedule monitoring has a 10 s stall limit. A healthy 1,800 s run has no total watchdog deadline.

Use `tools/jetson.py run` without `--wait`; the lead inspects journal/progress each minute and stops the named unit on missing progress or failed components. Keep bounded result logs and tegrastats from the existing workflow. Command launch/deploy/collect/push watchdogs remain separate. Anticipated disk: under 20 MB synthetic inputs, under 50 MB run logs and returned audio; models unchanged. Preserve unfinished output on failure. Diagnose once before any infrastructure retry.

Sample MemAvailable, system allocated swap, cumulative pswpin/pswpout, process-tree RSS/Swap, and major faults. Include the llama-server child. Capture once per second and at turn boundaries; report deltas separately for startup, idle, and active turns. Allocated swap is distinct from paging. System counters alone do not attribute another process's paging; store process counters and machine state. Report peak active headroom and detection rate; no snapshot proves turn safety. Queue sizes, unfinished lines/jobs, and mouth playback depth expose pending work. Keep sampling lock-free, and never query Edge from a telemetry thread.

Existing prompts omit encoded images in `Turn.prompt`, and sentence stops can omit final token usage (D86). Record model, context, image-token cap, text/history sizes, and an explicit unavailable prompt-token reason. Do not estimate exact template/image tokens or claim longer-context qualification. Exact prompt-token instrumentation is a separately verified prerequisite before changing context; this baseline can still establish answers, paging, and continuity.

Map retrieved runtime evidence to sources after a finished turn, on the scheduler thread, using authoritative `Memory.points` payloads and the fixed show intervals. Record capture timestamps, statement payloads, and raw retrieved IDs. Keep fixture source IDs separate from runtime-generated Edge point IDs. Match retrieved statement text to earlier actual ASR transcripts, rather than fixture answers. Missing or ambiguous mapping remains explicit. Record evidence-mapping elapsed time so its cost appears in scheduler lateness. Independent scoring uses these records; the harness never reads expected evidence.

## Acceptance before the baseline

Mac checks use a fake Robot, fake clock/audio, and tiny generated schedule. Include delayed ASR, split speech, and an empty transcript followed by another utterance. Subprocess checks stop the evaluator, crash it after a completion-ready row, and hang cleanup. Each preserves earlier rows, exits non-zero, leaves no child alive, and omits the footer. Prove one construction with no reset, fixed timing across visits, silence/audio pacing, correct row association, incremental failure evidence, no footer on missing/dead/stalled work, and a complete footer only after all counts and cleanup. Check absent WAVs and overlapping audio before startup. Tests must exercise failures rather than mirror methods. Run full repository checks and task review.

Then deploy the reviewed harness. Freeze a 90 s Jetson development smoke with two contiguous 45 s visits, two short MJPG source changes at 0/45 s, and four spoken events at 10/25/55/70 s: two auxiliary statements and two scored questions. Use derivatives from the already-used development live-items clip and newly synthesized unrelated text, with real models and every component active. No fresh challenge sources or wording enter this smoke. Require all counts, exact source/held-frame identities, correct interval association, zero lost input chunks, chunk/event lateness <= 0.5 s, no required thread loss, no detector stall over 10 s, and a zero worker exit before completion. Record turn failures and paging rather than accepting them as target passes. Do not read or score challenge questions. Verify source switches, frame identities/timing, liveness, incremental logs, counts, and counters. Only after that pass, the lead prepares and hashes the 63 frozen challenge utterances in a separate audio folder. Run the original 1,800 s schedule once for baseline and once for the selected candidate, without changed pacing or rubrics. Used results become development evidence after that comparison.
