# Claude Code Adversarial Review

Target: working tree diff
Verdict: needs-attention

Do not use these fixtures as the dialogue development or validation set for the booth goal. They have a reusable regression core, but they don't cover Qdrant knowledge, personal recall, visitor isolation, or irrelevant-memory suppression. Several recall checks are confounded or test a feature the runtime no longer ships.

Findings:
- [high] Shipped personal-fact recall (D206) and visitor isolation have no dialogue fixture (research/conversation.md:7-15)
  research/conversation.md:7-15 says statements are now scoped per visitor, enrolled and guest paths need separate acceptance checks, and 'live answer quality remains unmeasured'. The only Jetson check uses no models. None of the 68 dialogue turns plants a personal fact (name, preference, job) and recalls it after unrelated turns. None switches between two visitors to check for leakage, or enrolls a guest and checks that earlier statements carry over. exchanges.jsonl:5 (food) is the only personal-preference case, and it tests correction within one visitor. Deletion and restart appear only in exchanges.jsonl:1, for one visitor. Isolation, consent and enrolled-versus-guest behaviour are mandatory outcomes, and no scripted conversation covers them. This is an inference from the three fixture files plus the research note. I did not read the Jetson or unit checks, or eval/heldout.
  Recommendation: Add a small set of two-visitor conversations: A states a fact, B asks 'what did I tell you?' and must get no leak. Add guest-to-enrolled carryover, a consent decline, and a forget-then-recall check. Judge them with the existing contextual judge.
- [high] Qdrant knowledge, the booth's main value, is one buried turn and it fails (eval/dev/exchanges.jsonl:1)
  The only Qdrant-knowledge item is exchange-qdrant-1 ('What is Qdrant?') at exchanges.jsonl:1. The other dialogues in conversation.jsonl and the transfer file are generic (dinner, guitar, desk). research/conversation.md:37 says both prototype integrations failed the original Qdrant question even when its source was supplied. No fixture has a multi-turn Qdrant conversation with a pronoun follow-up. The deferred 'exact Qdrant recall failure' is also open (line 25). The 'vector search engine' rubric is a single yes/no on the 2B model's wording.
  Recommendation: Add three or four Qdrant dialogues, for example what it is, then how filtering works, then 'does that run on this robot?', with a correction turn. Write the rubrics against the Qdrant docs facts and the positioning line, not against vocabulary.
- [high] Image switches are forced and unrelated to the dialogue, so they confound the topic-follow signal (eval/dev/conversation.jsonl:1-3)
  All 18 turns in conversation.jsonl (lines 1-3) and all six in the transfer file alternate between two fixed images (m2-laptop and m2-pepsi) every one or two turns. The topics are dinner, guitar and plants, and no turn refers to the picture. Almost every rubric penalizes 'unrelated camera commentary' or 'an introduction', so the suite mostly checks that vision is suppressed. A booth visitor does not change the scene every other sentence. research/conversation.md:57 shows scene changes leave duplicate visitor questions without replies in history, so the fixtures conflate a real history-assembly bug with ordinary topic following. One image pair also means one prompt shape. There is no case where a visitor shows something relevant and then discusses it.
  Recommendation: Keep these dialogues as a regression-only 'scene change mid-dialogue' stress suite. In new dialogues, change the image only when the script says the visitor shows or moves something, and make the follow-up refer to it. Add a no-switch control arm so the two effects can be separated.
- [medium] Follow-ups depend on the model's earlier answer, and some rubrics have an escape hatch (eval/dev/conversation.jsonl:3)
  conversation-reading-2 ('What makes that different from a mystery?', conversation.jsonl:3) refers to a book genre the robot chose. Its rubric says 'A short clarification is acceptable if the preceding suggestion is ambiguous', so a non-answer can pass. desk-2, desk-4, dinner-2, trip-2 and plants-2 use 'that' or 'it' for a model-chosen referent (conversation.jsonl:1-3, transfer:1). Pass or fail then depends on how the first answer happened to go, and the rubric says only 'consistent with the preceding suggestion'. exchanges.jsonl:4 (book-recall) has the same problem and also accepts 'it never named a book'. Scripts that let the model pick the referent make a failed first turn cascade into the follow-up (research/conversation.md:57 notes this), so one bad turn is scored twice.
  Recommendation: Anchor follow-ups to visitor-supplied referents ('my houseplants', 'the five-minute practice'), and use a pronoun only when the previous turn fixed it. Remove 'clarification is acceptable' escapes. Score each follow-up conditioned on the first turn passing, or report first-turn and follow-up results separately.
- [medium] Recall of the robot's own replies tests a feature the runtime does not ship (eval/dev/exchanges.jsonl:1-6)
  The six *-recall turns (exchanges.jsonl:1-6) ask 'what city/company/book did you tell me about?'. They need stored assistant replies. research/conversation.md:11 says the current runtime adds neither stored assistant replies nor conversation summaries, and lines 19 and 27 treat complete-exchange retrieval as a deferred, archived prototype. Each dialogue pads five filler turns (2+3, joke, days in a week, bat, Mercury) to push the topic out of the four-exchange window. The same filler repeats across files, so it invites tuning to the filler. The user ranks random trivia as low priority.
  Recommendation: Demote to a named backlog suite for the deferred stored-exchange work, and drop it from the pass/fail gate. Replace it with recall of visitor-stated facts, which the shipped feature targets.
- [medium] Positive recall checks can pass from the robot's identity prior; some keyword checks are weaker than their rubrics (eval/dev/exchanges.jsonl:1-6)
  exchange-qdrant-recall asks 'What company did we talk about?' with expect_any ['qdrant'] (exchanges.jsonl:1). The robot is built by Qdrant, so it can say 'Qdrant' with no memory at all. The negative control exchange-windows-none (line 2) only partly offsets this. exchange-companies-recall (line 6) requires 'both Microsoft and Qdrant' in the rubric but accepts either in expect_any. 'What company built you?' also lets identity stand in for recall. exchange-food-correction (line 5) uses expect_any ['spicy'] and expect_none ['prefer mild']. An echo such as 'mild or spicy' passes the keyword while 'preferred mild' passes the exclusion, so the keyword layer is brittle. Judge verdicts then decide, which is fine, but the keywords add no independent signal.
  Recommendation: Use recall items whose answer cannot come from identity or world knowledge, such as a visitor-invented project name or a nonce preference. Use all-of semantics for multi-item recall. Keep the judge as the verdict and drop or label the keywords as sanity only.
- [medium] The suites sit near the floor with unexplained run variance, so they cannot rank candidates (research/conversation.md:43-50)
  research/conversation.md:47-50 shows the accepted baseline at 4/18 on conversation and 2/6 on transfer, with 7/18 to 4/18 variance on the same code and no confirmed cause. A swing of three of 18 turns exceeds most candidate deltas, and the prototype tied 4/18. The transfer result (2/6 versus 0/6) rests on two turns (research/conversation.md:52-57). Rubrics bundle content and negatives ('no introduction, no unrelated visual claims'), so a fail cannot be attributed to a cause. The reported numbers also show no repeat runs or per-clause scoring. I have not seen the judge. This is an inference from the published numbers. Because five patches were rejected against these same suites (archive index, line 73), they are also contaminated as a validation set. Transfer was explicitly 'frozen before the candidate runs' (transfer:1) but then used to reject one.
  Recommendation: Treat conversation.jsonl and the transfer file as regression-only. For any new comparison, run at least three repeats and split each rubric into a content pass and a leakage or visual-claim pass. Measure the judge's repeat agreement before trusting deltas.
- [medium] Irrelevant-memory suppression is only covered by one accidental case (eval/dev/conversation-transfer.jsonl:1)
  The one traced irrelevant-memory failure is conversation-language-1, where 'before a trip' matched about_past and supplied four unrelated desk exchanges (research/conversation.md:57; transfer:1). No fixture plants a memory and then asks an unrelated question that shares surface cues. The 'before' cue still admits future advice (line 25). The user explicitly wants irrelevant retrievals avoided.
  Recommendation: Keep language-1 and language-2 as regression for the about_past cue. Add two or three planted-memory conversations with lexical overlap and an unrelated question. Pair each with a relevant-question control so suppression does not become blanket refusal.
